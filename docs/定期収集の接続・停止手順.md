# 定期収集の接続・停止手順

対象は `iori-doiya/news-pocket` と `https://news-pocket.iori-sato-4637.workers.dev`。2026年10月15日の実装に対応します。秘密の値はこの文書に書きません。作業結果は制作記録の第1部14と検証報告へ記録します。

## 現在の接続

財務省・金融庁の公式RSSを使い、見出し・日時・URLだけを収集します。本文・写真・AI要約は使いません。115件の実取得から、新しい順で1回最大100件を本番D1へ登録する手動確認に成功しています。GoogleとD1は既存の接続を使い、再作成しません。

GitHubには収集用INGEST_TOKEN、VariablesにはSITE_URLを登録済みです。時刻実行はCOLLECTION_ENABLEDで制御します。サイトに表示するWorker側の同名変数は表示用で、GitHubの実行可否とは独立です。両方を揃えて運用してください。

## 収集を手動で確かめる

1. [GitHub Actions](https://github.com/iori-doiya/news-pocket/actions)を開き、左で **Collect news** を選びます。
2. **Run workflow** を開き、Branchに **main** を選び、緑の **Run workflow** を押します。停止フラグfalseでも、この手動操作は実行できます。
3. 実行一覧で新しい行を開き、**collect** → **npm run collect** を開きます。2情報源の取得件数と「登録対象100件。収集成功」、全体の緑の成功表示を確認します。初回検証では開発ブランチを選ぶ場合がありますが、普段はmainを使います。
4. 公開サイトを再読み込みし、上部と設定画面の「最終収集成功」が更新されたことを確認します。新着、テーマ切り替え、見出し、元記事リンクも確認します。

収集成功でも、新しい記事が毎回増えるとは限りません。同じURLは重複登録せず更新します。「100件」は登録・更新の対象数で、新規に増えた件数ではありません。1回100件に制限しているため、配信量によって過去の全記事を収録できません。

## 時刻実行の開始と停止

1. [リポジトリのVariables](https://github.com/iori-doiya/news-pocket/settings/variables/actions)を開きます。
2. **COLLECTION_ENABLED** の **Edit** で、開始は `true`、停止は `false` を入力して **Save variable**。SITE_URLは末尾スラッシュなしの上記公開URLです。
3. 開始前には手動実行の成功を確認してください。開始後は毎時17分の予定です。GitHubの混雑で遅延・実行省略があり、正確な時刻は保証されません。実行一覧のイベントが **schedule** の回を開き、成功を確認してください。
4. Workerの `wrangler.jsonc` → vars → COLLECTION_ENABLEDも同じ文字列にして `npm run deploy`。これは画面の案内を揃える操作です。GitHub側をfalseにすれば、Workerの表示がtrueでも時刻収集は止まります。手動実行と通常のサイト閲覧は停止しません。

停止フラグは課金のスイッチではありません。公開リポジトリと標準Ubuntuの実行環境、CloudflareのFreeプランを維持してください。有料プランへ変更する必要はありません。GitHubの活動が60日ないと定期実行が無効化される場合があります。[GitHubの公式仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 秘密キーの再接続

通常は登録済みのキーを変更しません。CloudflareとGitHubに同じ値が必要です。漏えい時の交換は両サービスで行ってください。

PowerShellで実行フォルダを `C:\Users\ユーザー\OneDrive\ドキュメント\news-pocket` にします。Node.js 24がPATHにある環境では以下を実行します。

```powershell
cd "C:\Users\ユーザー\OneDrive\ドキュメント\news-pocket"
npm run connect:collection
```

この命令は `.secrets/ingest-token.txt` がなければ専用キーを作り、既存なら再利用し、Cloudflare Secretsへ登録します。成功時は登録済みの案内だけを表示し、秘密の値を出力しません。Wranglerの認証が切れている場合は `npx wrangler login` で本人がログインします。Cloudflare側でWorkerが存在する必要があります。

GitHubで **Settings → Secrets and variables → Actions → Secrets → New repository secret** を開き、Nameに `INGEST_TOKEN`、Secretに同じ私有ファイルの値を入力し **Add secret**。既存の場合はEditを使います。成功すると一覧に名前が表示され、値は表示されません。秘密は `.secrets/` 以外のソースファイルやコマンド引数、チャットへ貼り付けないでください。

## エラーを調べる

| 表示 | 確認する場所と対応 |
|---|---|
| ジョブがSkipped | VariablesのフラグとPublicかを確認。Privateへ変えた場合は無料運用前提を確認するまで再開しない |
| 401 | CloudflareとGitHubのINGEST_TOKENが一致しているか。値を公開して照合しない |
| 503 | サイト設定のDB応答、DATA_MODE=live、Free確認、Secretsを確認。Cloudflare Workers → news-pocket → Logsで一般的な分類を確認。原因を特定せずに設定を何度も変えない |
| 特定の情報源の取得失敗 | 公式RSS案内・URL・配信終了や条件変更を確認。本文ページのスクレイピングで代替しない |
| 日時が進まない | 部分失敗・全失敗は最終成功を据え置く設計。Actionsで直近の実行と失敗元を確認 |

取得前に、90日を過ぎた未保存記事・失効セッション等の整理も実行します。容量の値はD1の実容量そのものではなく、内容量から計算する余裕を持った見積もりです。実容量と無料枠はCloudflare **Storage & databases → D1 → news-pocket-db → Metrics**、Workersの回数は **Compute → Workers & Pages → news-pocket → Metrics** で確認します。

## 情報源を止める・更新を戻す

配信条件が不明になった情報源は `config/sources.json` の該当enabledをfalseにして、検査・公開を行います。次の整理でその記事と保存参照が消えるので、元に戻しても保存参照の復活は保証されません。全情報源を止める場合は先にGitHubのフラグをfalseにします。情報源0件のlive公開は公開前検査で止まるため、必要ならDATA_MODE=sampleで停止案内を出します。

失敗したコード更新は、まず収集をfalseで停止し、GitHubの該当コミットを `git revert <コミットID>` で打ち消して検査・公開します。操作の詳細は[制作記録・運用手順書](制作記録・運用手順書.md)の復旧手順を参照。コードを戻してもD1のデータは自動では戻りません。
